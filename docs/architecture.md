# Architecture

Owner: Khan (Backend Lead). Contract: `contracts/openapi.yaml`, `contracts/explanation.schema.json`. Specs it implements: `docs/specs/api-access-control.md`, `docs/specs/api-audit-log.md`, `docs/specs/engine-matching.md`. All data is synthetic.

## 1. Components

```
 officer app ─┐                      ┌── Postgres 16  (system of record for access, links, audit)
 admin panel ─┴─ HTTPS/JSON ─ API ───┤
        (types generated from        └── Neo4j 5 Community (case graphs, SAME_AS edges, traversal)
         contracts/openapi.yaml)      │
                                      └── engine (Python package, called in-process; no I/O to Postgres)
                                      └── audit anchor file (outside the database, append-only)
```

| Component                           | Responsibility                                                                                                                                                                                                    |
| ----------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| API (`backend/tracex_api`, FastAPI) | Authentication, the access-control policy function, redaction, review and access-request workflows, pending changes, audit writes, OpenAPI contract. The only writer of Postgres.                                 |
| Engine (`backend/tracex_engine`)    | Ingest, extraction, case graphs, matching, scoring, SAME_AS edges in Neo4j. Jurisdiction-blind. Never imports the API, never writes audit rows. Returns transition records and run records.                       |
| Postgres                            | Users, sessions, cases, assignments, documents, a link index with explanation payloads, stubs, access requests and grants, pending changes, settings, audit log.                                                  |
| Neo4j                               | Entity nodes, case-graph edges (owns, called, transferred to, seen at) and SAME_AS edges with `link_id`, score, gates, evidence and history. Used for blocking, 2-hop neighbourhoods, cluster and path traversal. |
| Audit anchor                        | One line `{seq, row_hash, at}` appended to `AUDIT_ANCHOR_PATH` every 60 s and on shutdown, only after a verify passed, and it names the row that verify checked. The database credentials cannot write it.        |

| Reconciliation                     | **Human decisions.** The decision, `link_history` and the audit row commit in Postgres **first**, with a `decision_outbox` row (`decision_id`, link, expected state, target state, actor, reason). The engine is called only after that commit, idempotent on `decision_id`; a retry worker and the startup reconcile replay every outbox row without an acknowledgement until the engine has applied it. A crash between commit and engine call leaves the decision in effect and audited, and the edge converges; a crash before commit leaves both stores unchanged and no audit row. Decisions on one link are serialised in the API (a row lock on the `links` row held from the state check to the outbox insert, and a per-link lock around the engine call), because the engine's compare-and-set keys on a millisecond `updated_at` and is not a lock. **Engine answers.** The engine answers an applied decision with a record or one of four codes: `STATE_MISMATCH`, `ILLEGAL_TRANSITION`, `NOT_FOUND` (no edge with that id: never created, withdrawn, or a Neo4j restore) and `REPLAY_CONFLICT` (the `decision_id` was applied with other arguments). The API pre-validates under the row lock, so none of the four can come from a correct request: every one is divergence, never a client response. Each is alerted and left in the outbox unacknowledged for the reconcile; `NOT_FOUND` is a different repair from `STATE_MISMATCH` (the edge is missing, so the reconcile recreates nothing and raises the alert for the operator). **Engine runs.** The engine has already changed Neo4j when it returns; if the API dies before persisting the records, the startup reconcile sweeps Neo4j against Postgres and writes what is missing: (1) every edge whose `match_run_id` or `decision_id` is not in Postgres is imported as `links`, `link_history` and audit rows; a run id found on an edge but missing from `match_runs` gets a stub `match_runs` row (status FAILED, error_code `RECONCILED`, counts empty) so the foreign key holds; (2) an engine withdrawal deletes the edge, so no unseen run id remains to find: every live Postgres link (state not WITHDRAWN) with no Neo4j edge is imported as WITHDRAWN (system actor, run id if known) with LINK_WITHDRAWN audited. **Rejected and forged changes.** A transition record whose `from` state does not equal the Postgres state is rejected: nothing is written to Postgres and **the Neo4j edge is reverted** to the Postgres state (state, score, history as stored), the system audit event ENGINE_DIVERGENCE_REVERTED is written and an alert is raised; alerting alone is not enough, because the edge would otherwise stay wrong until the next run. The same applies at reconcile: Reconcile never imports a `decision_id` that is not in `decision_outbox`; it reverts that edge change to the Postgres state, writes ENGINE_DIVERGENCE_REVERTED and alerts, so a forged Neo4j write never becomes an audited human decision. An edge change is never left un-audited. **Guards.** A matching run starts only when `decision_outbox` has no unacknowledged row (409 `RUN_IN_PROGRESS`), and while a run is RUNNING confirm, reject, undo and reopen answer 409 `RUN_IN_PROGRESS`, so a run never reads an edge that lags a committed decision. Thresholds are validated (`Thresholds.validated`, which raises `ThresholdsError`) **before** the `match_runs` row is created as RUNNING, so an invalid setting is a 422 and never a stuck run. Pair uniqueness in Neo4j rests on the one-RUNNING-run guard (the store reads then writes the pair without a lock). |

## 4. Database roles: who may write what

| DB role           | Rights                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                     |
| ----------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `tracex_migrator` | Owns every table, trigger and function; runs migrations; nothing else uses it.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                             |
| `tracex_api`      | The only role the API connects with. `SELECT, INSERT` on application tables; `UPDATE` only where a row has a state (sessions, refresh tokens, links, access requests and grants, pending changes' state, upload batches, match runs, `decision_outbox`). `users`, `user_coverage`, `case_assignments` and `threshold_versions` have no direct `INSERT` or `UPDATE`: they change only through the `SECURITY DEFINER` function `apply_change(change_id)`, which checks state APPROVED and the stored hash, so four-eyes is structural. No `DELETE` anywhere except `sessions`, `refresh_tokens` and `login_attempts`, and `link_cited_lines`, a table derived from the payload that is rebuilt on every refresh. On `audit_log` and `audit_detail_key_owner`: `INSERT` and `SELECT` only (the registry: `SELECT`). Not owner, not superuser, not a member of the owner role; no `ALTER`, `TRIGGER`, `GRANT`. |

Application roles map to writes only through endpoints: JUNIOR writes access requests and withdrawals; INVESTIGATOR adds confirm and reject; SUPERVISOR adds undo, reopen and the approval or revocation of access requests; SENIOR adds approval of pending changes and audit verification; ADMIN writes uploads, matching runs and change proposals; the system writes engine transitions, expiries and grant closures. Nothing a user does reaches a table without passing the policy function.

## 5. Audit table

`audit_log` follows `api-audit-log.md` section 2 column for column: `seq` bigint primary key (contiguous from 1), `event_id`, `occurred_at`, `event_type`, `outcome`, `actor_kind`, `actor_user_id`, `actor_role`, `actor_district_id`, `reason_code`, `refs jsonb`, `target_type`, `target_id`, `resolved_target` (private), `detail jsonb`, `session_id`, `request_id`, `client_ip`, `row_nonce bytea(16)`, `prev_hash`, `row_hash`.

| Control                       | How                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                  |
| ----------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Not alterable by the API role | Row trigger `BEFORE UPDATE OR DELETE` and statement trigger `BEFORE TRUNCATE` raise; `tracex_api` has `INSERT` and `SELECT` only and cannot alter triggers (section 4). A superuser could still drop the triggers: detected, not prevented.                                                                                                                                                                                                                                                                                                                                          |
| Hash chain                    | `row_hash` is SHA-256 over `prev_hash` followed by the canonical form of every column except `row_hash`, including `row_nonce`. Appended by `audit.append` under `pg_advisory_xact_lock`, last step before commit. W2 rows commit with the action; W3 rows (denials, auth failures) are appended in their own transaction.                                                                                                                                                                                                                                                           |
| External head anchor          | `{seq, row_hash, at}` appended to a file outside the database every 60 s, on every verify and on shutdown. The anchor is written by a separate OS user or sidecar (or the file is set append-only with `chattr +a`), so the API's own OS user cannot truncate it. `POST /audit/verify` and startup (last 1000 rows plus the anchor) check the chain reaches the anchor and hashes match; failure blocks `/ready`. The head is also copied into the runbook by hand (D28). Honest limit: someone with database owner rights and write access to the anchor can still rewrite history. |
| Reader never sees internals   | The API returns `row_ref` (HMAC of row and reader), never `seq`, `event_id`, hashes, nonce, session, request or client address. `detail` is serialized through a per-event allow-list that excludes every class P key (`seq_from`, `seq_to`, `range_*`, `head_seq`, `anchor_seq`, `first_bad_seq`). The one exception is `first_bad_seq` in a BROKEN `POST /audit/verify` result to a SENIOR.                                                                                                                                                                                        |

**Verify, the 503 gate and the nightly job (PR #30 item 12, N1).**

- A missing, empty or unreadable anchor file counts as BROKEN (`first_bad_seq` 1) once the log has more than one row. A log that holds only `AUDIT_CHAIN_STARTED` may lack one, and the API writes the first anchor at startup. After that, an anchor lost with its volume must be restored from backup; the API never invents one for a log with history.
- The API verifies at startup and keeps the result in memory. `/ready` returns the cached result and runs a new tail verify (last 1000 rows plus the anchor) at most once every 60 seconds, so unauthenticated callers cannot trigger more work. A 60-second background loop re-verifies and appends an anchor only when the verify passed; the anchor holds the `seq` and `row_hash` of the last row that verify walked, never a head read afterwards. Shutdown runs a fresh verify and anchors only when it passes. The nightly job and `POST /audit/verify` anchor the same way. The tail verify always reaches back to the last anchor, so rows that arrived since it are never skipped. An empty log (no `AUDIT_CHAIN_STARTED`) is BROKEN.
- The gate fails closed: unless the latest verify returned OK, every route except `GET /health`, `GET /ready` and `POST /audit/verify` answers 503 `NOT_READY` and serves no data. That includes the time before the first verify has run. Any exception in a startup, periodic, `/ready` or `POST /audit/verify` check counts as not OK and raises the alert once. An anchor line that is not a JSON object is skipped like a malformed line. The 503 body is the fixed `SafetyPauseError` of the contract. A later passing verify (the loop or `POST /audit/verify`) clears it. An alert is raised when the state turns BROKEN.
- `python -m tracex_api.verify_audit` is the nightly job: a full chain walk plus the anchor check, then the four-eyes cross-check below. It prints one JSON line, writes an `AUDIT_VERIFY_RUN` row for the SYSTEM actor, appends an anchor only when everything is clean, logs every problem at error level and exits 1 on any problem. It needs only `DATABASE_URL` and `AUDIT_ANCHOR_PATH`, so any scheduler can run it (see the runbook).
- **Four-eyes limit (N1).** The API connects with one database login. The database stops `tracex_api` inserting a decided row and checks that an approval names an active SENIOR distinct from the proposer and the subject with the proposed hash (migration `0004`), but it cannot prove which person approved: a compromised API can insert a PENDING row, set it APPROVED in the name of any active senior, and `apply_change` will apply it. This is the floor without a database identity per officer. The control is detection: the nightly job checks that every APPROVED `pending_changes` row has a `CHANGE_APPROVED` audit row for the same change id, the same decider and an equal `change_hash`, and reports every row that does not.

**Engine store lost (N3).** At startup the reconcile sweep marks a link WITHDRAWN when the engine no longer has its edge. If the engine store holds no edge at all while Postgres has live links, the store was lost (a new Neo4j volume, or the in-memory engine after a restart); the sweep withdraws nothing, raises an alert, and `/ready` stays 503. The sweep does not retry: the alert stays and `/ready` stays 503 until an operator restores the store (or replays the batches) and restarts the API. Only the first sweep after process start fails stale RUNNING match runs, so a run started during the replay is never interrupted. The sweep withdraws nothing while a match run is RUNNING and waits for it to end. While the store is lost, routes still serve the links Postgres holds; the alert is the signal.

Constraints that make the D40 minors structural, not just policy:

| Minor                             | Constraint or rule                                                                                                                                                                                                                                                                                                                                                                                                            |
| --------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| (a) read rule (d)                 | Row-level filter: a system event reaches ADMIN or SENIOR under rule (d) only when `refs = '[]'`; for a SENIOR also only when every user and district the row names (target, subject, old and new values; actors without a jurisdiction do not count) is inside coverage. Rows with any case reference are judged by rules (a), (b), (c) alone.                                                                                |
| (b) encrypted cursor              | Every list cursor is authenticated-encrypted (AEAD, server key from the environment) over `(reader_id, canonical filters, sort, position, expiry)`, so its contents cannot be read. Position is the visible sort key plus `row_ref`, never `seq` or an id. A cursor from another reader, with other filters, expired (15 minutes) or tampered with answers the same 422 as a malformed one. Empty pages return a null cursor. |
| (c) case-level access, owned keys | Rule (c) uses case-level access (own case, own jurisdiction, coverage) and never grants. `audit_detail_key_owner` gives every `detail` key an owning case; `audit_log_refs_cover_detail` (a `BEFORE INSERT` trigger plus the application check W7) rejects a row whose `refs` do not cover the cases its `detail` keys and `target_id` reveal, and rejects unknown keys.                                                      |
| (d) denied probe (D39)            | `audit_log_unresolved_has_no_refs`: `CHECK (target_type <> 'UNRESOLVED' OR refs = '[]'::jsonb)`. A denied lookup of a hidden or non-existent id is stored identically (`UNRESOLVED`, the string supplied or its `hmac:` form, empty `refs`); the resolved target goes to the private `resolved_target` column, never returned by the API.                                                                                     |

## 6. Engine and API boundary

The engine is a library the API imports. It reads and writes Neo4j and returns plain data; it does not open Postgres connections and does not know about users, roles or districts.

| Direction      | What crosses                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                     |
| -------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| API to engine  | `ingest(batch)`, `run_matching(input_case_ids, triggered_by, thresholds_version, thresholds)`, `apply_decision(link_id, expected_from, to_state, actor_user_id, decision_id, reason_code, reason_text)` (engine spec section 6; the engine answers `STATE_MISMATCH`, `ILLEGAL_TRANSITION`, `NOT_FOUND` or `REPLAY_CONFLICT` with nothing changed, so the API pre-validates under the row lock and treats every one of the four answers as divergence to alert on, never as a client response). `run_matching` raises `ThresholdsError` before running when the thresholds are invalid; the API validates first and maps it to 422                                                                                                                                                                                                                                                                                                                                                |
| Engine to API  | Edges to index, and one **transition record** per change: `{link_id, from, to, actor ("engine" or user id), match_run_id, decision_id, reason_code, at}` (`to` null for WITHDRAWN; `decision_id` null for engine transitions, `match_run_id` null for human decisions; engine spec errata PR #12), plus the **run record**                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                       |
| API afterwards | One Postgres transaction per batch of records: upsert `links` and `link_history`, refresh `link_cited_lines`, close grants whose evidence now cites a line outside the fixed ranges (EVIDENCE_CHANGED) or whose link is REJECTED, UNDONE or WITHDRAWN, write one audit row per record (LINK_AUTO_CREATED, LINK_SUGGESTED, LINK_DEMOTED, LINK_PROMOTED, LINK_WITHDRAWN, system actor), persist the run record. The set of links to refresh is every `link_id` in `transitions` **plus** `RunResult.updated_link_ids` (edges the run rewrote without a state change: new score inside a band, a thresholds-version rerun, a reopened edge): for each, `engine.explanation(link_id)` supplies score, band, gates, thresholds, ruleset, both entity and case ids and the payload, so `links`, `link_cited_lines` and grant closure never lag the edge. Rows are written only for what the engine returned; a transition the engine did not record (a failed write) is never audited. |

Rules the boundary keeps: scores never feed back into weights; the explanation payload is stored as the engine produced it, validated against the schema and never edited in place; at read time the API adds only the optional `page`, `document_type` and `case_number` of the same source document to each source, and `masked`.

**Read-time overlay and `document_id` mapping.** The stored `explanation jsonb` is never edited, so it lags a human decision (the decision commits in Postgres first, before the engine call). Every read therefore overlays two things from Postgres: `state` from `links.state`, and `history` from `link_history` (engine entries with `reason_code` DEMOTED, PROMOTED or WITHDRAWN or null for a creation; every human decision with null `reason_code` in the payload, the human's reason code living on `link_history`). The engine names a source document by its file name inside the case; the API replaces `source.document_id` with `documents.id` for `(case, file_name)` at read time, and applies the same map when it computes `link_cited_lines` from the payload and when it fills `entities.source_document_id`.

## 7. One request: confirm a link

`POST /links/{link_id}/confirm` as INVESTIGATOR bharat.

1. Middleware authenticates: signature, algorithm pinned, `exp`, `sid` live, `ver` equals the user's `authz_version`. Failure: 401 and an `AUTH_TOKEN_REJECTED` row in its own transaction (W3).
2. Load the caller (role, district, active) from Postgres. Claims for role or district are ignored.
3. Policy: load the link and both end cases. If the caller lacks ALLOW on any end (worst outcome wins), or there is no such link: 404, identical body and headers for both, and an `ACCESS_DENIED` row (`UNRESOLVED`, empty `refs`, reason `R2_NOT_VISIBLE`) appended after the business transaction (W3).
4. Role check: below INVESTIGATOR, or a cross-district or cross-state link without a covering SENIOR, or access only through a grant: 403, `ACCESS_DENIED` with `http_status` 403.
5. State check: the transition must be legal (SUGGESTED or AUTO to CONFIRMED) and match `expected_state` if given; else 409.
6. Refuse with 409 `RUN_IN_PROGRESS` if a matching run is RUNNING. Open one transaction. `SELECT ... FOR UPDATE` the `links` row (this serialises decisions on one link) and re-check the state; the engine call in step 8 takes a per-link in-process lock as well.
7. In the same transaction: update `links`, insert `link_history`, insert the `decision_outbox` row, close grants made moot by the change, and call `audit.append` for `LINK_CONFIRMED` (`previous_state`, `new_state`; no reason or personal values). If the append fails, roll back and answer 500 with no data (W1, W2).
8. Commit. Postgres plus the audit row are now the record. Then call `engine.apply_decision(...)` (idempotent on `decision_id`) and mark the outbox row acknowledged; on failure the retry worker and startup reconcile replay it. Return the updated `LinkDetail`.
9. A crash between 7 and 8 leaves both stores unchanged and no audit row; a crash after the commit leaves the decision in effect and audited, and Neo4j converges.

Every request connection sets `lock_timeout` to 5 s: a request that cannot get a row lock in that time fails with 500 and rolls back, so no request waits behind a stuck transaction for longer. An unexpected error rolls the transaction back before the 500 is built.

## 8. Keys, accepted residuals

- A matching run is scoped by upload batch (or every batch not yet run) and always matches new input against all loaded cases; its result for ADMIN is totals of AUTO and SUGGESTED created only (no LOW count, no per-case or per-pair counts). The totals come from `RunRecord.created_by_state` and nowhere else: `counts_by_state` counts every settled pair including existing edges and `NONE` (the Low count), and `counts_by_band` has LOW, so neither is stored in a column an API response reads and neither is returned. The engine still receives `input_case_ids`, derived from the batches.
- The JWT signing key, the cursor key, the `row_ref` key and the `hmac:` key are four distinct secrets from the environment; none is derived from another.
- The `.env.example` keys and passwords start with `dev-only` and are public. The API refuses to start on any of them (the four keys, `TRACEX_API_DB_PASSWORD`, the password in `DATABASE_URL`), and `migrate` and `seed` refuse the same set plus `TRACEX_MIGRATOR_DB_PASSWORD`, every `TRACEX_SEED_PASSWORD_*` and the password in `DATABASE_ADMIN_URL`, unless `TRACEX_ALLOW_DEV_SECRETS` is exactly `1`. Compose passes the flag through from `.env`; `.env.example` sets it for local development and CI; a real deployment never sets it. A refused start leaves `/health` answering and `/ready` at 503.
- The explanation payload is validated against `contracts/explanation.schema.json` after masking and before it leaves the API. A payload that fails is not sent: the route answers 500 `INTERNAL` and an alert names the failing JSON path and keyword, never a value. The API image copies the schema from the repository `contracts/` folder (compose `additional_contexts`), and the API will not start without it.
- The trap modifier (SHARED, HUB, MULTI_USER) in an explanation reveals that an identifier occurs in other cases, possibly hidden ones. Accepted residual: no count and no ids are shown.
- An ADMIN who names a district and case number to upload can learn whether that case number exists in that district (also through the 422 on an assignment proposal). Accepted residual; a case number alone is not case data.
- A stub is unlabelled, but the number of stubs on an entity equals its hidden links (access spec section 4).
