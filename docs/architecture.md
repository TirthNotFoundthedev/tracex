# Architecture

Owner: Khan (Backend Lead). Contract: `contracts/openapi.yaml`, `contracts/explanation.schema.json`. Specs it implements: `docs/specs/api-access-control.md`, `docs/specs/api-audit-log.md`, `docs/specs/engine-matching.md`. All data is synthetic.

## 1. Components

```
 officer app ─┐                      ┌── Postgres 16  (system of record for access, links, audit)
 admin panel ─┴─ HTTPS/JSON ─ API ───┤
        (types generated from        └── Neo4j 5 Community (case graphs, SAME_AS edges, traversal)
         contracts/openapi.yaml)      │
                                      └── engine (Python package, called in-process; no I/O to Postgres)
                                      └── audit anchor file (outside the database, append-only)
```

| Component                           | Responsibility                                                                                                                                                                                                    |
| ----------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| API (`backend/tracex_api`, FastAPI) | Authentication, the access-control policy function, redaction, review and access-request workflows, pending changes, audit writes, OpenAPI contract. The only writer of Postgres.                                 |
| Engine (`backend/tracex_engine`)    | Ingest, extraction, case graphs, matching, scoring, SAME_AS edges in Neo4j. Jurisdiction-blind. Never imports the API, never writes audit rows. Returns transition records and run records.                       |
| Postgres                            | Users, sessions, cases, assignments, documents, a link index with explanation payloads, stubs, access requests and grants, pending changes, settings, audit log.                                                  |
| Neo4j                               | Entity nodes, case-graph edges (owns, called, transferred to, seen at) and SAME_AS edges with `link_id`, score, gates, evidence and history. Used for blocking, 2-hop neighbourhoods, cluster and path traversal. |
| Audit anchor                        | One line `{seq, row_hash, at}` appended to `AUDIT_ANCHOR_PATH` every 60 s, on every verify and on shutdown. The database credentials cannot write it.                                                             |

## 2. Postgres versus Neo4j

| Question                           | Answer                                                                                                                                                                                                                                                                                                                  |
| ---------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Who decides what a viewer may see? | Postgres only. Access rows (users, assignments, districts, grants) and the policy function live there. Neo4j holds no access data and is never queried by a request without the policy applied to the result.                                                                                                           |
| Where is a link's state of record? | Neo4j holds the SAME_AS edge the engine wrote; Postgres `links` is the index the API reads, filters, pages and joins against. Both carry the same `link_id`, state, score and payload. The API updates the Postgres row from every transition record and decision in the same transaction as the audit row (section 6). |
| Why both?                          | Neo4j for traversal (clusters, paths, 2-hop evidence). Postgres for transactions, constraints, paging, joins to access rows and the audit chain.                                                                                                                                                                        |
| Cluster membership                 | Derived on read from active edges; never stored. Cluster and path ids returned to a client are random per response and not derived from members (D33).                                                                                                                                                                  |
| Reconciliation                     | A decision calls the engine first (idempotent on `decision_id`), then commits Postgres. If the commit fails, the next startup reconcile re-applies from the engine's edge history and the request is not reported as done.                                                                                              |

## 4. Database roles: who may write what

| DB role           | Rights                                                                                                                                                                                                                                                                                                                                                                             |
| ----------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `tracex_migrator` | Owns every table, trigger and function; runs migrations; nothing else uses it.                                                                                                                                                                                                                                                                                                     |
| `tracex_api`      | The only role the API connects with. `SELECT, INSERT, UPDATE` on the application tables above as listed in the W column; no `DELETE` on `links`, `link_history`, `threshold_versions`; on `audit_log` and `audit_detail_key_owner`: `INSERT` and `SELECT` only (the registry: `SELECT`). Not owner, not superuser, not a member of the owner role; no `ALTER`, `TRIGGER`, `GRANT`. |
| `tracex_readonly` | `SELECT` for reporting and the grep-style tests; not used by the API.                                                                                                                                                                                                                                                                                                              |

Application roles map to writes only through endpoints: JUNIOR writes access requests and withdrawals; INVESTIGATOR adds confirm and reject; SUPERVISOR adds undo, reopen and the approval or revocation of access requests; SENIOR adds approval of pending changes and audit verification; ADMIN writes uploads, matching runs and change proposals; the system writes engine transitions, expiries and grant closures. Nothing a user does reaches a table without passing the policy function.

## 5. Audit table

`audit_log` follows `api-audit-log.md` section 2 column for column: `seq` bigint primary key (contiguous from 1), `event_id`, `occurred_at`, `event_type`, `outcome`, `actor_kind`, `actor_user_id`, `actor_role`, `actor_district_id`, `reason_code`, `refs jsonb`, `target_type`, `target_id`, `resolved_target` (private), `detail jsonb`, `session_id`, `request_id`, `client_ip`, `row_nonce bytea(16)`, `prev_hash`, `row_hash`.

| Control                       | How                                                                                                                                                                                                                                                                                                  |
| ----------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Not alterable by the API role | Row trigger `BEFORE UPDATE OR DELETE` and statement trigger `BEFORE TRUNCATE` raise; `tracex_api` has `INSERT` and `SELECT` only and cannot alter triggers (section 4). A superuser could still drop the triggers: detected, not prevented.                                                          |
| Hash chain                    | `row_hash = SHA-256(prev_hash                                                                                                                                                                                                                                                                        |     | canonical(all columns except row_hash))`, including `row_nonce`. Appended by `audit.append`under`pg_advisory_xact_lock`, last step before commit. W2 rows commit with the action; W3 rows (denials, auth failures) are appended in their own transaction. |
| External head anchor          | `{seq, row_hash, at}` appended to a file outside the database (`O_APPEND`, never rewritten). `POST /audit/verify` and startup (last 1000 rows plus the anchor) check the chain reaches the anchor and hashes match; failure blocks `/ready`. The head is also copied into the runbook by hand (D28). |
| Reader never sees internals   | The API returns `row_ref` (HMAC of row and reader), never `seq`, `event_id`, hashes, nonce, session, request or client address. The one exception is `first_bad_seq` in the verify result (SENIOR only).                                                                                             |

Constraints that make the D40 minors structural, not just policy:

| Minor                             | Constraint or rule                                                                                                                                                                                                                                                                                                                                                       |
| --------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| (a) read rule (d)                 | Row-level filter: a system event reaches ADMIN or SENIOR under rule (d) only when `refs = '[]'`. Rows with any case reference are judged by rules (a), (b), (c) alone.                                                                                                                                                                                                   |
| (b) signed cursor                 | Every list cursor is an HMAC (server key from the environment) over `(reader_id, canonical filters, sort, position)`. A cursor from another reader, with other filters, or tampered with answers the same 422 as a malformed one. Empty pages return a null cursor.                                                                                                      |
| (c) case-level access, owned keys | Rule (c) uses case-level access (own case, own jurisdiction, coverage) and never grants. `audit_detail_key_owner` gives every `detail` key an owning case; `audit_log_refs_cover_detail` (a `BEFORE INSERT` trigger plus the application check W7) rejects a row whose `refs` do not cover the cases its `detail` keys and `target_id` reveal, and rejects unknown keys. |
| (d) denied probe (D39)            | `audit_log_unresolved_has_no_refs`: `CHECK (target_type <> 'UNRESOLVED' OR refs = '[]'::jsonb)`. A denied lookup of a hidden or non-existent id is stored identically (`UNRESOLVED`, the string supplied or its `hmac:` form, empty `refs`); the resolved target goes to the private `resolved_target` column, never returned by the API.                                |

## 6. Engine and API boundary

The engine is a library the API imports. It reads and writes Neo4j and returns plain data; it does not open Postgres connections and does not know about users, roles or districts.

| Direction      | What crosses                                                                                                                                                                                                                                                                                                                                                        |
| -------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| API to engine  | `ingest(batch)`, `run_matching(thresholds_version, thresholds)`, `apply_decision(link_id, to_state, actor_user_id, decision_id, reason)`                                                                                                                                                                                                                            |
| Engine to API  | Edges to index, and one **transition record** per change: `{link_id, from, to, actor ("engine" or user id), match_run_id, reason_code, at}` (`to` null for WITHDRAWN), plus the **run record**                                                                                                                                                                      |
| API afterwards | One Postgres transaction per batch of records: upsert `links` and `link_history`, refresh `link_cited_lines`, close grants whose evidence now cites a line outside the fixed ranges (EVIDENCE_CHANGED) or whose link is REJECTED or UNDONE, write one audit row per record (LINK_AUTO_CREATED, LINK_SUGGESTED, LINK_DEMOTED, system actor), persist the run record. |

Rules the boundary keeps: scores never feed back into weights; the explanation payload is stored as the engine produced it and validated against the schema; the API adds only the optional `page`, `document_type` and `case_number` fields to each source.

## 7. One request: confirm a link

`POST /links/{link_id}/confirm` as INVESTIGATOR bharat.

1. Middleware authenticates: signature, algorithm pinned, `exp`, `sid` live, `ver` equals the user's `authz_version`. Failure: 401 and an `AUTH_TOKEN_REJECTED` row in its own transaction (W3).
2. Load the caller (role, district, active) from Postgres. Claims for role or district are ignored.
3. Policy: load the link and both end cases. If the caller lacks ALLOW on any end (worst outcome wins), or there is no such link: 404, identical body and headers for both, and an `ACCESS_DENIED` row (`UNRESOLVED`, empty `refs`, reason `R2_NOT_VISIBLE`) appended after the business transaction (W3).
4. Role check: below INVESTIGATOR, or a cross-district or cross-state link without a covering SENIOR, or access only through a grant: 403, `ACCESS_DENIED` with `http_status` 403.
5. State check: the transition must be legal (SUGGESTED or AUTO to CONFIRMED) and match `expected_state` if given; else 409.
6. Open one transaction. `SELECT ... FOR UPDATE` the `links` row. Call `engine.apply_decision(...)` (idempotent on `decision_id`) and receive the transition record.
7. In the same transaction: update `links`, insert `link_history`, close grants made moot by the change, and call `audit.append` for `LINK_CONFIRMED` (`previous_state`, `new_state`; no reason or personal values). If the append fails, roll back and answer 500 with no data (W1, W2).
8. Commit. Return the updated `LinkDetail`. A failure between step 6 and 8 is repaired by the startup reconcile and the client sees an error, never a half result.
